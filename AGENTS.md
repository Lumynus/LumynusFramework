# AI Agent Guidelines - Lumynus Framework

This document defines mandatory rules, engineering standards, and behavioral guidelines for any AI agent working on this project.

---

## 1. Golden Rule: Do Not Reinvent the Wheel

> [!IMPORTANT]
> **Strictly use the native classes, methods, and features provided by Lumynus.**
> It is strictly forbidden to rewrite utilities, create manual helper functions, or install third-party libraries for functionality that the framework already provides natively and optimized.

Before proposing or implementing any solution, verify whether Lumynus already provides a helper, utility, or service for the task. Examples:
- **Brazilian Formats and Documents:** Use `Brasil` (`$this->brasil()->validarCPF()`, `formatarCNPJ()`, `realBrasil()`, `dataParaSQL()`, etc.).
- **Data Conversion:** Use `Converter` (`$this->converter()->toInt()`, `toPascalCase()`, `toSnakeCase()`, `xmlToArray()`, etc.).
- **Sanitization:** Use `Sanitizer` (`$this->sanitizer()->string()`, `email()`, `url()`, `normalizeWhitespace()`, etc.).
- **Rule Validation:** Use `Validate` and `Requirements` (`$this->validate()->check()`, strict regexes in `Requirements::*`).
- **File Management:** Use `File` (`$this->file()->read()`, `save()`, `rename()`, etc.).
- **Secure Encryption:** Use `Encryption` (`$this->encryption()->encrypt()`, `decrypt()`, etc.).
- **External HTTP Requests:** Use `HttpClient` or `LumaHTTP` (`$this->httpClient()->request()`).
- **State & Traffic Management:** Use `Cookies` (`$this->cookies()`), `Sessions` (`$this->sessions()`), and `QueueManager` (`$this->queue()`).
- **Routing & Middlewares:** Use `Route` with built-in parameter and type validation.
- **Rendering & Templates:** Use the secure `Luma` template engine (`$this->view()`).

## 3. Clean Code & Architectural Quality

All generated or modified code must strictly adhere to Clean Code best practices:

1. **Mandatory Strict Typing:**
   - Every PHP file must begin with `declare(strict_types=1);`.
   - All properties, parameters, and return types must have explicit strict typing.
2. **Coherent, Decoupled Architecture:**
   - Controllers must extend `AbstractController`.
   - Middlewares must extend `AbstractMiddleware` and implement `handle()`.
   - Terminal commands must extend `AbstractCommand`.
   - Use inherited shortcuts from controllers and middlewares to access services (`$this->cookies()`, `$this->sessions()`, `$this->brasil()`, etc.).
3. **Single Responsibility Principle (SRP):**
   - Keep functions concise and single-purpose.
   - Decouple business logic from routes, templates, and commands.
4. **Exception Handling:**
   - Use semantic exceptions and throw appropriate errors upon validation or security failures.

## 4. DocBlocks in the User's Language

- **Mandatory Documentation:** Every class, public/protected method, parameter (`@param`), return type (`@return`), and thrown exception (`@throws`) must include clear, structured PHPDoc DocBlocks.
- **User Language:** DocBlocks generated by the agent must match the user's preferred language and machine locale settings (in a Portuguese environment, document in clear and professional Portuguese; in an English environment, document in English).
- **Consistency:** Maintain standard PSR-5 / PHPDoc formatting.

---

## 5. AI Agent Checklist

When fulfilling any user request, make sure to:
- [ ] Read `https://lumynus.dev/llm-docs.txt` to understand the recommended native approach to solving the problem.
- [ ] Do not rewrite or reinvent any native Lumynus feature.
- [ ] Enforce `declare(strict_types=1);` and strict types on parameters and returns.
- [ ] Follow framework inheritance and conventions (`AbstractController`, `AbstractMiddleware`, `AbstractCommand`).
- [ ] Generate comprehensive DocBlocks matching the user/machine environment language.
- [ ] Validate file syntax with `php -l` before finishing the task.

must not be committed to Git. Every application must add `/application.json`

### HTML pages and API formatter

Views configured in `errors.pages` are used only when the negotiated response
format is HTML. The resolver searches for `.luma`, then `.html`, and uses the
framework's default HTML page if neither exists or rendering fails. These views
do not define the JSON, XML, or text response envelope.

Applications that operate as APIs must configure `errors.formatter` with a
class that implements `Lumynus\Contracts\ErrorFormatter`. The formatter is
responsible for the JSON/XML body and the plain-text message. For HTML, return
`null` from `html()` and let `ErrorResponder` use the configured page or the
default fallback.

Example API formatter:

```php
<?php

declare(strict_types=1);

namespace App\Infrastructure\Http;

use App\Domain\Respostas\EnvelopeDeRespostaDomain;
use Lumynus\Contracts\ErrorFormatter;
use Lumynus\Http\Errors\ErrorPayload;

/**
 * Formats framework errors according to the e_hub API standard.
 *
 * ErrorResponder calls this class for JSON, XML, or text responses.
 * The domain builds the { mensagem, codigo, dados } envelope in pt-BR.
 */
final class FormatadorDeErros implements ErrorFormatter
{
    /**
     * Builds the body used for JSON and XML.
     *
     * @param ErrorPayload $erro Normalized error data.
     * @return array<string, mixed> API envelope.
     */
    public function body(ErrorPayload $erro): array
    {
        return EnvelopeDeRespostaDomain::erro(
            EnvelopeDeRespostaDomain::mensagemPadrao($erro->status),
            $erro->status
        );
    }

    /**
     * Builds the plain-text message.
     *
     * @param ErrorPayload $erro Normalized error data.
     * @return string|null Message in pt-BR.
     */
    public function text(ErrorPayload $erro): ?string
    {
        return EnvelopeDeRespostaDomain::mensagemPadrao($erro->status);
    }

    /**
     * Keeps the configured HTML pages in control.
     *
     * @param ErrorPayload $erro Normalized error data.
     * @return string|null Always null to delegate to the HTML resolver.
     */
    public function html(ErrorPayload $erro): ?string
    {
        return null;
    }
}
```

Configure the class with its fully qualified name in `application.json`:

```json
"errors": {
  "formatter": "App\\Infrastructure\\Http\\FormatadorDeErros",
  "pages": {
    "404": "errors/404",
    "default": "errors/default"
  }
}
```

The formatter must not treat the framework message as trusted public text. Use
the HTTP status to select a public, translated message so internal details such
as `Route produtos/x not found` are not exposed through the API.
